# HW2 — стратегии устойчивости

Учебный мини-фреймворк для stateless-сервиса с исходами 2xx, 4xx, 5xx и клиентским таймаутом. Реализованы все шесть стратегий из [задания DDIA HW2](https://docs.google.com/document/d/1MjuyZjjSaFK2F6j1hvgXuHwCDASOXTukdnZq374JdEU/edit).

## Запуск

Нужен Go **1.25+**. Зависимостей вне стандартной библиотеки нет. Для `-race` используется обычная поддержка race detector в Go, включая доступный C-компилятор на платформах, где он требуется.

Из корня репозитория:

```sh
./test.sh
```

Скрипт сам переходит в `hw2/`, запускает `go vet ./...` и `go test -race -count=1 -timeout=60s ./...`, возвращает ненулевой код при ошибке. Его можно вызвать и по абсолютному пути из другого каталога.

Отдельный тест из `hw2/`:

```sh
go test -race -run TestRoundRobinOrderAndBackoffComposition -v ./resilience
```

HW2 — отдельный Go-модуль `github.com/Murzabek0312/highload_prog/hw2`. Для запуска не нужны Docker, PostgreSQL, Grafana или код первого задания.

## API

Пакет `resilience` выделяет три интерфейса:

```go
type Sender interface {
    Send(ctx context.Context) (Response, error)
}

type Client interface {
    Do(ctx context.Context, sender Sender, budgets Budgets) (Response, error)
}

type MultiClient interface {
    Do(ctx context.Context, senders []Sender, budgets Budgets) (Response, error)
}
```

`Response` содержит `StatusCode` и `Body []byte`. Отправитель возвращает 2xx/4xx/5xx через `Response`; зависание моделируется ожиданием отмены контекста. Сценарий ответов и задержек задается при создании тестового отправителя, а не передается в `Send`.

Sender обслуживает один логический запрос и его подзапросы. Он обязан завершать `Send` при отмене контекста. Клиент управляет deadline и таймаутом; Sender не получает отдельные числовые таймауты или параметры стратегии. Как и в стандартном API Go, `ctx` должен быть ненулевым. В пул передаются самостоятельные отправители для разных реплик.

Настройки стратегии задаются полями структуры, бюджеты — аргументом `Do`. Счетчики бюджетов и курсор round-robin создаются заново на каждый вызов `Do`. Состояние circuit breaker общее для всех запросов одного `*CircuitBreaker`.

| Стратегия | Настройки | Поведение |
|---|---|---|
| `Default{}` | Только временные бюджеты | Ровно одна попытка, если отмена или некорректные параметры не предотвратили запуск |
| `Retry{}` | Все бюджеты | Последовательные повторы без задержки |
| `Backoff{InitialDelay, Multiplier}` | Положительная задержка, конечный коэффициент > 1 | Растущие задержки после 5xx и таймаутов |
| `RoundRobin{Strategy}` | Последовательный `Client`; `nil` означает `Retry{}` | Каждый фактический `Send` переходит к следующей реплике по кругу |
| `Hedging{Delay}` | Неотрицательная задержка | Первая реплика сразу, остальные одновременно по таймеру, если успеха еще нет |
| `&CircuitBreaker{FailureThreshold, Cooldown, Strategy}` | Положительный порог K и время T; `Strategy` как в `RoundRobin` | Round-robin с временным исключением реплик после K ошибок подряд |

В `RoundRobin.Strategy` можно передать `Backoff{InitialDelay: 10 * time.Millisecond, Multiplier: 2}`: порядок реальных вызовов останется `A → B → C → A`. Backoff получает один вращающийся Sender, поэтому дополнительный retry-loop не возникает. Собственная реализация `Client`, переданная в round-robin, также должна вызывать Sender последовательно и соблюдать общие бюджеты.

## Бюджеты

Все лимиты относятся к одному логическому запросу, включая обращения к разным репликам.

| Поле `Budgets` | Семантика |
|---|---|
| `MaxAttempts` | Максимум фактических вызовов Sender, включая первый; для стратегий с повторами должен быть > 0 |
| `MaxFastErrors` | Остановка на N-й ошибке 4xx |
| `MaxFailures` | Остановка на N-й ошибке 5xx |
| `MaxTimeouts` | Остановка на N-м таймауте отдельной попытки |
| `Latency` | Положительный общий бюджет времени: попытки, backoff и hedging delay |
| `SubrequestLatency` | Ограничение одной попытки; 0 использует оставшийся общий бюджет времени |

Бюджеты ошибок неотрицательны. **0 и 1 оба означают остановку после первой ошибки соответствующего типа.** Значение 2 позволяет пережить одну ошибку этого типа, но останавливает выполнение на второй. Ошибки разных типов считаются отдельно. Например, 4xx и 5xx расходуют по одной единице двух разных счетчиков.

Попытка запускается только при доступном общем бюджете и времени. После результата проверяются бюджет его типа и общий лимит попыток; если одновременно исчерпаны оба, ошибка содержит обе причины. Успех на последней разрешенной попытке считается успехом.

Для `Default` число попыток фиксировано равным 1, как `max_retries=1` в ТЗ. `Default` и `Hedging` используют только `Latency` и `SubrequestLatency`: числовые retry/error-бюджеты для них не применяются. Hedging делает не больше одного обращения к каждой реплике.

Внешняя отмена или более ранний deadline вызывающего кода имеют приоритет. Таймаут отдельного подзапроса может привести к повтору; истечение общего времени завершает весь запрос. Ответ, полученный на deadline или после него, не считается успехом.

## Принятые трактовки ТЗ

- **4xx:** повторяется без задержки. В backoff такая ошибка не увеличивает и не сбрасывает накопленную задержку.
- **Backoff:** после k-й тяжелой ошибки задержка равна `InitialDelay × Multiplier^(k−1)` с точностью `time.Duration`. Каждый раз она вычисляется от исходного значения, чтобы округление не останавливало рост при дробном множителе. Рост ограничен диапазоном `time.Duration`. Если задержка не оставляет времени на попытку до deadline, стратегия сразу завершается с `ErrLatencyExhausted` и последним ответом сервера, не дожидаясь deadline. После исчерпания попыток дополнительного ожидания нет.
- **Hedging:** таймер `Delay` начинается после допуска первой попытки к отправке. Если первая реплика быстро ответила ошибкой, остальные все равно запускаются по этому таймеру. Ошибка не побеждает последующий 2xx. При ошибках всех реплик стратегия ждет общего deadline, как указано в ТЗ. `Delay=0` разрешает немедленный запуск остальных после запуска первой попытки.
- **Завершение hedging:** после первого успеха остальные попытки отменяются; `Do` дожидается завершения запущенных горутин. Это опирается на обязательную реакцию Sender на отмену. Горутины, игнорирующие контекст, принудительно остановить нельзя.
- **Circuit breaker:** расширяет `RoundRobin` и принимает ту же последовательную стратегию, например `Backoff`. Считает 4xx, 5xx и таймауты попытки; внешняя отмена не учитывается. После K ошибок подряд исключает реплику на T, затем возвращает со сброшенным счетчиком; успешный ответ сбрасывает счетчик.
- **Время жизни состояния:** состояние хранится в `*CircuitBreaker` и общее для последовательных и параллельных запросов (защищено mutex). Для каждого запроса создаются новые Sender, поэтому реплика определяется позицией в списке: порядок отправителей должен быть одинаковым во всех запросах. Экземпляр нельзя копировать после первого использования.
- **Все реплики отключены:** запрос сразу завершается ошибкой `ErrAllReplicasOpen`, как в классическом circuit breaker, без ожидания cooldown. Пропуск исключенной реплики не расходует попытку.

Неожиданные ошибки Sender вне модели ТЗ и неподдерживаемые статусы завершают последовательную стратегию без повторов. В hedging они считаются неуспехом этой реплики: другие реплики еще могут вернуть успех.

## Ошибки

Причины доступны через `errors.Is`: `ErrInvalidConfig`, `ErrInvalidResponse`, `ErrAttemptsExhausted`, `ErrFastErrorsExhausted`, `ErrFailuresExhausted`, `ErrTimeoutsExhausted`, `ErrLatencyExhausted`, `ErrSubrequestTimeout`, `ErrAllReplicasOpen`.

При таймаутах также сохраняется `context.DeadlineExceeded`, при внешней отмене — `context.Canceled` и заданная вызывающим кодом причина отмены. Для 4xx/5xx последней попытки статус можно получить через `errors.As` в `*StatusError`.

При остановке по счетчику ошибок или числу попыток возвращаются последний ответ сервера и ошибка. При отмене или истечении времени возвращается пустой `Response`; исключение — ранний отказ от задержки backoff, превышающей остаток бюджета. Hedging при исчерпании времени возвращает общую причину, а не отдельные ошибки реплик.

## Устройство и проверка

- `client.go` — интерфейсы, ответ сервера и проверка отправителей.
- `budget.go` — лимиты запроса, проверка значений и отдельные счетчики ошибок.
- `errors.go` — причины остановки и ошибка ответа сервера.
- `attempt.go` — одна попытка и классификация результата.
- `context.go` — проверка отмены и deadline, отменяемое ожидание.
- `default.go`, `retry.go`, `backoff.go` — одиночный запрос и общий последовательный цикл повторов.
- `round_robin.go` — адаптер Sender с выбором реплики по кругу и точкой расширения для исключения реплик.
- `hedging.go` — координатор параллельных одиночных запросов через `Default`.
- `circuit_breaker.go` — общее состояние реплик и правило исключения; подключается к round-robin.

Smoke-тесты находятся в `*_test.go` рядом с реализацией. Сценарный Sender расположен только в тестах. Каждый тест выделяет `Given`, `When`, `Then`. Проверяются не только ответы, но и число вызовов, порядок реплик, моменты запуска, отмена и завершение активных запросов.

Временные и конкурентные сценарии используют [testing/synctest](https://pkg.go.dev/testing/synctest) с виртуальным временем. Ключевые проверки: смешанные ошибки → успех; границы каждого бюджета; общий deadline; последовательность задержек; round-robin с backoff; одновременный запуск hedged-попыток; отмена проигравших; исключение реплик между запросами, сброс счетчика после успеха и cooldown, breaker с backoff, параллельные запросы; некорректные параметры и внешняя отмена. Тесты таймаутов также проверяют, что причина не дублируется в тексте ошибки.
